01摘要

本报告记录把 MiniMind（jingyaogong/minimind，2.6K+ star 的迷你中文 LLM 全流程训练项目）从 「研究代码」重构为「训练项目」形态的完整过程。重构以本工作区产出的 skills/ml-dev-spec 为方法论， 每一处改动都可回溯到规范的具体章节；重构过程中的每一次取舍，都在对应章节留下了"为什么"。

诊断 → 对策

对原版 17 个源文件逐文件研读，提炼 19 条不满意清单（每条有代码证据）， 全部映射到 ml-dev-spec 的对策。最大的痛点不是模型代码，而是五个训练脚本之间 ~300 行的复制粘贴。

evidence-based零测试

架构 → 落地

src 布局五分离（参数/数据/模型/训练流程/横切工具），8 个训练范式收敛为 「common 基件 + 同构薄子包」；KV cache 从每步 cat 改为预分配 + 原地切片。

src layout8 stages

验证 → 交付

43 个单元测试（KV cache 一致性 / 停止三重 / loss mask 逐 token / 配置守门人）全绿； 八范式 tiny 冒烟 + torchrun 双卡 DDP 冒烟通过；64M 模型完整 pretrain→SFT→DPO 训练产出可对话权重（官方 minimind-3 同构）。

43 testsDDP×2
一句话结论：原版 minimind 的模型代码质量高于其工程 reputation（QK-Norm、MoE 直通估计器、 fp32 数值纪律都是对的）；真正欠账在工程层——配方散落、无验证评估、无测试、日志靠 print。 重构因此采取「模型层保真移植 + 工程层推倒重来」策略，state_dict 键级兼容官方权重。

03形态判定：为什么是"训练项目"而不是"研究代码"

ml-dev-spec 的第一个问题是形态判定（project-structure §1）：代码被谁消费、变化最快的是什么。 原版 minimind 是标准的研究代码形态——单人、单文件模型 + 单文件训练脚本、README 即复现手册， 这个形态本身没有错。但重构的目标场景是持续实验平台：换数据、换架构、跑对照实验、 多个训练范式共存——这正是"训练项目"形态的判据。

形态判据原版 minimindminimind_reborn
代码被谁消费自己跑实验（教学展示）长期实验 + 后续复现改进（对照 P1-P5 路线）
变化最快的是什么模型结构（教学演示）训练流程（按范式扩展：pretrain→SFT→DPO→RL）
规范强度最轻src 五分离 + yaml 配置 + 生命周期钩子 + 完整测试
反方向的克制：形态升级不等于无限工程化。我们没有引入配置模式 E（vLLM 式单一事实源 + AST 提取文档）、 没有做 Docker 矩阵、没有把推理层做成 vLLM 式五层引擎——配置项 ~60 个且稳定，模式 C 足够； 推理只需要单卡内核。规范强度跟着判据走，不跟着炫技走。

4.2 同构子包：新增一个训练范式还剩多少事

原版新增一个范式 = 复制一个 300 行脚本。重构后，pretrain 与 sft 的 workflow 各只有 ~30 行， 二者的 diff 是数据集类与权重名：

src/minimind_reborn/training/sft/workflow.py完整文件——这就是"一个范式"的全部
def run(cfg: RunConfig, *, device=None, local_rank=0) -> Trainer:
    setup_logging(cfg.run_dir)
    tokenizer = load_tokenizer()
    model = build_model(cfg, tokenizer)
    train_ds, eval_ds = build_lm_dataset(cfg, tokenizer, kind="sft")

    def compute_loss(batch, m):
        out = m(batch["input_ids"], labels=batch["labels"])
        loss = out.loss + out.aux_loss
        return loss, {"train/loss": out.loss.item(), "train/aux_loss": float(out.aux_loss)}

    trainer = Trainer(cfg, model, tokenizer, train_ds, eval_ds,
                      compute_loss=compute_loss, save_weight="full_sft",
                      device=device, local_rank=local_rank)
    trainer.run()
    return trainer
seed/AMP/梯度累积/裁剪/续训/评估/保存/日志/指标全部不在场——它们在 Trainer 里被正确地做了一次。 这是本次重构最大的单点收益：同一段逻辑不再有八份手抄拷贝——改一处，八个训练范式同时受益。

05关键决策：六次"怎么做"背后的"为什么"

5.1 配置：模式 C（分域 dataclass + yaml 配方）与守门人

configuration §1 的三问选型：配置只被 Python 消费（需要类型与默认值）→ dataclass 系； 按训练范式增长 → 分域；一次实验 = 超参集合 → 平面配置。模式 C 胜出。 守门人（validate_and_derive）承担三类职责，全部在解析期 fail-fast：

职责例真实事故现场
未知 key 报错train.num_workers（属于 data 域）开发中守门人真的拦住了我自己写错的冒烟配方——这正是"拼错 key 静默用默认值训练"的防线
类型断言train.learning_rate=abc 拒绝；=false 接受小写布尔字符串 "0.001" 覆盖 float 是经典事故
派生推导head_dim/intermediate_size/moe_intermediate_size 用 None 哨兵，推导后填值用户手填派生值必漂移（官方公式 ceil(h·π/64)·64 收敛到一处）

5.2 可追溯四件套：只拿到输出目录，能重建这次训练吗

logging-metrics §4 的完整性判据是本次重构最有效的"验收问题"。每次训练运行落盘：

文件内容回答什么
train.log生命周期事件 + 降级留痕（rank0 独占）过程中发生了什么
metrics.jsonl(step, key, value) 三元组，jsonl 后端永远启用数值如何变化（断网不失忆）
config.json完整配置快照（同时进 checkpoint）什么配置
env.jsongit commit + dirty、python/torch/cuda、GPU、seed什么环境

5.3 权重存档两套制：训练存档管续训，推理单文件管部署

原版一份 fp16 权重兼任推理与续训，两个语义互相伤害（续训丢精度、推理文件过大）。 重构后拆开：checkpoints/ 下的 resume 文件存 fp32 主权重 + optimizer + scaler + 进度 + 配置快照 + best + RNG 状态（位精确恢复，含跨卡数 step 换算）； out/ 下的推理权重存 fp16（原子写）。resume 严格加载、finetune 逐 key warning 双语义分开。

5.4 KV cache：预分配 + 原地切片的不变量

llm-inference §2 的四条不变量逐条落实，最关键的一条用测试锁死：

tests/test_models/test_kv_cache.py有无 cache 的自回归生成必须逐位一致
def test_generation_cache_consistency(tiny_model):
    result = generate(model, prompt, gen_cfg, eos_token_id=None, pad_token_id=0)
    seq = result["sequences"]
    cur = prompt                       # 参考实现：每步全量前向（无 cache）贪心
    for _ in range(24):
        logits = model(cur).logits[:, -1, :]
        cur = torch.cat([cur, logits.argmax(dim=-1, keepdim=True)], dim=1)
    assert (seq == cur).all(), "带 cache 的生成与全量重算不一致"

注意力在带 cache 的步进路径坚持走显式 mask 分支（SDPA 的 is_causal 语义与位置偏移不匹配）， causal mask 只作用于当前步新位置块——scores[..., -seq_len:] += triu(-inf) 这行是全系统最贵的单行代码，配了注释与测试。

5.5 依赖准入：从 30 个精确锁死的包到 3 个核心依赖 + 4 组可选扩展

判据一句话："没有它 import 主包就失败"才进核心。最终核心依赖 3 个： torch>=2.14,<3、transformers>=5.16,<6、pyyaml>=6。 两个典型取舍：

  • HF datasets 被标准库取代：原版用它加载 jsonl，我们用字节偏移索引 （一次 O(N) 扫描建索引，__getitem__ 为 O(1) seek+read）——内存与文件大小无关，省掉 2GB 传递依赖；
  • requests 不进核心：只有 SGLang rollout 引擎（可选 extras 路径）需要，惰性 import。

5.6 RL 系：为什么 rollout 型范式不走 Trainer 基件

GRPO/PPO/agent 的循环结构是"先采样、后更新"，与 pretrain 型的"逐 batch 梯度下降"不同构。 强套基件会把钩子系统做得很重。取舍：三个 RL workflow 保留自己的循环（忠实移植原版算法语义）， 但四件套落盘、保存/续训、精度上下文、奖励函数（官方三份重复实现合并为一）全部下沉到 RLSession 与 common/rewards.py。基件服务同构部分，不假装覆盖异构部分。

已知取舍：RL 循环不做梯度裁剪前的 scaler 语义（原版 RL 用 bf16 无 scaler，保持一致）； loss-mask 的模式匹配机制依赖 chat template 恰好产出 <|im_start|>assistant\n 序列—— 机制保留官方设计（保证权重/数据互通），但用逐 token 断言测试锁死（tests/test_data/test_loss_mask.py）。
