01摘要

重训计划阶段 2（SFT@1536 全量训练，runs/sft_full_lc/20260929_004524，双卡 DDP）运行中期暴露两个问题，本报告完成调查、定位与方案设计，按决定：当前训练继续跑完、代码暂不修改，本报告仅留档。

问题一：数据管线喂不饱 GPU——显卡 0 号间歇完全空转（功耗在 73W↔352W 之间猛跳）、1 号恒定满载（那是在通信里空等慢的那张卡）、算力利用率（MFU，实际有效计算占理论峰值的比例）只有 10-15%、瞬时速度 53K-138K 字/秒剧烈波动。根源：单条训练样本的编码偶尔极慢，而预取缓冲太小兜不住——超长的对话样本在做「整轮保留」适配时要把全文重新分词 5-20 多次，最极端的样本（66,977 字）单条编码就要几秒；缓冲里只有 16 个批次，被一条慢样本拖住后 GPU 只能干等。预计总时长 ~40h，超出计划（26h）约 55%。

案 B（调查顺带发现）：LR 余弦退火分母双倍 bug——trainer.py:213 的 full_iters 未除以 world_size，DDP 下每 rank 实际迭代数只有它的一半，导致学习率余弦退火的进度分母是实际步数的 2 倍——训练结束时学习率退不到预期的下限 1e-6（此句的终值 5.5e-6 后经复审修正为 2.32e-6，见 §04.25）。已用日志数字反推验证（见 §04）；9 月 25 日的上次全量 SFT 同样受此影响（非本次新引入）。

修复方案分四层（P1 对症主因 / P2 管线参数 / P3 LR bug / P4 验证流程），均已设计到改动点与验收断言级别，列入 §08 待执行清单——暂缓执行，待当前训练完成或另行批准后排期。

02现象与证据

2.1 GPU 侧：典型的「等数据」特征

12 秒内 6 次连续采样（训练日志同时段仍在正常推进，排除卡死）：

解读：GPU1 的恒 100% 不是在干活——双卡训练要求每步两端汇合，先算完的那张卡会在通信环节空转等慢的一张（功耗并不高）；被数据卡住的那个 rank（GPU0=rank0，快卡 4090 且兼任日志/保存）才真正 0% 空闲。GPU 利用率在 0% 与 100% 之间振荡，是数据管线喂不满的标准症状（外部资料佐证见 §07）。

2.2 日志侧：步时分布证明「GPU 本身可达水位」

对本次 run 前 1491 个日志窗口的量化：mean 245ms/micro-step、median 239ms、p10 184ms、p90 310ms、min 134ms。最好的窗口 134ms/step 对应 183K tok/s（MFU≈21%）——说明 GPU + 主循环本身能达到接近预期的水位，中位数以上多出的 ~110ms/step 全是间歇性停顿。吞吐日志的 53K-138K 波动与之自洽。

2.3 系统侧：CPU 大量空闲反而印证「延迟瓶颈」

CPU load 仅 4.4/32 线程、内存余量 14G、温度远低于降频线（54-64°C / 42-51°C，风扇 47%/30%——热与负载全部在正常区间，长跑无风险）。若瓶颈是 CPU 算力不足，load 应接近饱和；「CPU 大量空闲 + GPU 间歇空转」的组合指向「前一批没编完、后面全排队」的延迟问题，而不是 CPU 算力不够的吞吐问题。

2.4 tok/s 口径说明

日志 tok/s 的分母是填充口径（bs × world × max_seq_len = 8×2×1536 = 24,576/micro-step，trainer.py:262-264），与 MFU 公式自洽。100K tok/s ≡ 245ms/step。本报告所有吞吐数字均为此口径。

03根因分析：吞吐瓶颈（案 A）

3.1 主因：SFT 单样本编码的重复 tokenize 与重尾

encode_sft_sample（data/datasets.py:195-243）的调用链存在三类浪费：

#问题代码位置量化影响
①公共路径无条件 tokenize ×2：L216 全文渲染+tokenize 得 full_ids，L224 无论是否做过轮次适配都重新「渲染+tokenize」一遍——81.3% 未超预算样本的成本被白白翻倍datasets.py:216 / 224常态样本成本 ×2
②轮次适配的迭代式全文重编码：_fit_turns（L144-192）中每个 fits() = 1 次 apply_chat_template + 1 次全文 tokenize；丢轮用二分搜索（ceil(log2(max_drop)) 次）；user 内容截短循环每圈只砍 20% 字符却重新全文渲染+tokenize（L189）datasets.py:144-192超预算样本（18.7%）单次编码 5-20+ 次全文渲染+tokenize；20 万字符级 user 内容要 15-20 圈
③渲染本身不便宜：chat template 是 3,895 字符的 Qwen 式 jinja（含 tools 分支+双向消息循环），逐条调用（非批量）datasets.py:122-141每样本至少 2 次、超预算样本 5-20+ 次

叠加数据的重尾（len_profile 实测：渲染长度 mean 1219 / p90 2322 / p99 7900 / max 66,977 token），单条 __getitem__ 可达秒级；一个 batch（8 样本在同一 worker 内串行编码）含一条超长样本，整批交付延迟 1-6 秒。

3.2 放大器：预取缓冲太小，偶发的慢样本直接让 GPU 空等

  • DataLoader 参数（utils/seed.py:53-58）：pin_memory=True、num_workers=8（启动命令覆盖，yaml 里是 4），但 prefetch_factor 默认 2、persistent_workers 默认 False——每 rank 缓冲仅 16 个 batch（约 2-4 秒计算量）；
  • CUDAPrefetcher（prefetch.py:15-52，无条件启用）只负责把已就绪的数据从内存搬上显卡（毫秒级，不是瓶颈），且缓冲深度只有 1、取数时会原地等编码完成——帮不了编码慢的问题；
  • 主线程同步点：SFT 的 compute_loss 内部 .item()（training/sft/workflow.py:22）+ 训练循环 running_loss += loss.item()（trainer.py:260）——worker 队列一旦见底，等待时间全额计入步时；
  • 数据加载严格按顺序交付：第 N 批没编完，第 N+1 批（哪怕早已编好）也不能先上——前面卡住、后面全排队。

04顺带发现：LR 余弦退火分母双倍 bug（案 B）

4.1 机制

trainer.py:213：

full_iters = (len(self.train_ds) + t.batch_size - 1) // t.batch_size

len(train_ds) 是全量样本数，但 DDP 下 DistributedSampler 给每 rank 只分配一半样本，每 rank 实际迭代数 ≈ full_iters / 2。而 LR 调度用它当分母：

total_micro = cfg.train.epochs * full_iters          # = 2 × 592,046 = 1,184,092
global_micro = epoch * full_iters + offset            # 2 epochs 实际只走到 ≈ 592,046

余弦退火的进度 global_micro / total_micro 永远只走到 50%。

4.2 日志数字反推验证（完全吻合）

当前进度 146,500 步、实测 lr = 9.66e-6。按错误分母计算：进度 = 146,500 / 1,184,092 = 12.4%；cosine 半程公式 lr = 1e-6 + 9e-6 × (1+cos(π×0.124))/2 = 9.66e-6 —— 与日志一致，bug 确认。

4.25 复审修正（2026-09-29 13:00，独立复核后追加）

bug 本身经独立验证成立（暂停点 lr=9.63e-6 与带 bug 分母的公式预测 9.633e-6 完全吻合；按正确分母应为 8.59e-6，对不上）。但本报告 §04 的终值推算有误：「2 epochs 跑完时 LR 退到半程 ~5.5e-6」忽略了 epoch 1 的 global_macro 从 full_iters 起步（global_micro = epoch×full_iters + offset）——实际结束时进度为 75%（非 50%），终值 ≈2.32e-6，比本报告原估计的更接近 1e-6 下限，损害轻于原文描述。已用 test_old_bug_signature_locked 单测锁定该签名。另：重训计划会话此前按日志 ETA 汇报「剩余 9.5-10h」同样有误（ETA 只计当前 epoch 剩余），实际剩余 ~29h。

4.3 影响评估

  • 本 run：2 epochs 结束时 LR 停在 ~2.32e-6（而非 1e-6 下限；初稿误写 5.5e-6，见 §04.25），退火末端（通常对应质量最好的训练阶段）缺失；
  • 历史影响：9 月 25 日的上次全量 SFT（sft_full，同样双卡 DDP + 同一代码）受同样影响——此前未被发现；pretrain 同代码路径，上次 pretrain_full（2×4090）大概率同受影响（未逐一核验，修复时以单测锁定）；
  • 单卡训练不受影响（world_size=1 时口径恰好正确），这也是 mini 时代（部分单卡验证）未暴露的原因之一。

05修复方案（P1-P4，留档设计，暂不执行）

P1（对症主因）：编码路径整体移到 token 域

  • P1a 复用 full_ids：未做轮次适配（81.3% 样本）时直接使用 L216 的 full_ids，跳过 L224 的重复渲染+tokenize——公共路径成本立即减半，改动 ~5 行；
  • P1b 重写 _fit_turns 为「一次 tokenize + 切片」：整段 tokenize 一次得到 full_ids，用现有 _match_at 在 token 序列中定位各轮边界（轮次以 <|im_start|> 等特殊 token 分隔，特殊 token 是天然 BPE 边界，从整段结果中定位边界与整段 tokenize 零等价性风险），之后丢轮 = 列表切片、user 截短 = token 域左截（按超出 token 数 × 平均字节/token 一次截足）——超预算样本从 5-20+ 次渲染+tokenize 降为 1 次；
  • 正确性保障：等价性单测——修复前后同 seed、同样本逐 token 一致（含 input_ids / labels / spans 三对齐）；
  • 预期：整体 encode CPU 成本下降 60-70%（81% 样本 ×2→×1，18.7% 样本 ×5-20→×1）。

P2（管线参数，放大器消除）

  • prefetch_factor=4、persistent_workers=True（utils/seed.py 的 loader 参数）——缓冲从 16 batch 加深到 64 batch，吸收重尾；
  • num_workers 8→16（CPU load 仅 4.4/32，大量余量）；
  • compute_loss 去 .item()（改 loss.detach()，日志窗口再同步物化）——消除每步两次主线程同步点。

P3（LR bug）

  • full_iters 按 dist.get_world_size() 折算（或 total_micro 改用 iters × epochs 实际口径）；
  • DDP 语义单测：模拟 world_size=2 的调度序列，断言 2 epochs 结束时 LR = 下限值 lr×min_ratio；
  • 历史注记：9/25 的 sft_full（及大概率 pretrain_full）同受影响，对比实验结论需考虑此因素。

P4（验证流程，动手门槛）

  • 全量单测绿 → 等价性单测绿 → 60 步冒烟吞吐对照：≥150K tok/s（当前 ~100K）才允许动任何在跑训练；
  • 冒烟同时断言：LR 数值与修复后调度公式一致。

预期综合收益

P1+P2 落地后 SFT@1536 吞吐预期从 ~100K 恢复到 150-183K tok/s（最好窗口已证明 GPU 可达 183K），单次 SFT 时长从 ~40h 压回 22-27h（计划口径内）。对档二链路（续训 + 第二次 SFT + 可能的决策点触发的再训）累计可省 15-30h GPU。

07资料对照

7.1 内部资料适用性修正

docs/pretrain_readiness.md §2「2 个 worker 即饱和、数据侧上限 12×、瓶颈纯在 GPU」的结论不适用于本场景：该实测用的是 PretrainDataset + pretrain_t2t_mini + seq 340 的轻路径（单次 tokenize + 截断，无 chat template 渲染、无轮次适配、无 Python span 扫描、无重尾）。SFT@1536 的单样本编码成本高一个数量级以上且带重尾（p99=7900/max=66,977），「2 workers 饱和」不可外推。建议 readiness 文档补一条适用范围注记（列入 §08 待执行清单 P5）。

7.2 外部佐证

  • GPU 利用率在 0% 与 100% 之间振荡 = 数据管线喂不满的标准症状，第一调节杠杆是 DataLoader（io.net《GPU Utilization Optimization》）；
  • persistent_workers=True 避免每 epoch 重建 worker、prefetch_factor 在 I/O/编码尾延迟场景上调至 4-8+、pin_memory=True 近零成本加速 H2D——多来源共识（pierce.dev《Debugging Slow PyTorch Training》实测了 prefetch_factor 高至 200 的组合；stevengong.co《PyTorch Performance Tuning》"keep the GPU fed"）；
  • DDP 场景下 prefetch 与共享内存（/dev/shm）联动调优（PyTorch GitHub issue #10670）。
