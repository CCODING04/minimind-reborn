03问题是什么（背景与现状）

3.1 训练管线如何损坏了数据（机制 + 实测数字）

问题一：预训练阶段，45% 的 token 从未进入训练。预训练窗口只有 380 token，数据集中 30.7% 的文档超过这个长度。超长文档被截断丢弃的部分实测占全部 token 的 45.2%（保留率 54.8%）。长文档恰恰是模型学习「长距离上下文」的原料。

问题二：SFT 阶段的截断方式产生三种损坏。SFT 窗口 768 token，50.6% 的会话超长（多轮对话子集 82.3% 超长）。旧的截断方式是「保留前 768 个 token」：

损坏机制实测数字
不完整回复被当作学习目标回复结尾被切掉、开头仍在窗口内，损失区间判定把它当作学习目标每条受损样本平均 0.82 个残段——模型反复学「没有结尾的半截话」，与生成实测中「回答戛然而止、复读」直接对应
零损失样本截断把所有完整回复都切掉，全部标签 -100，损失恒 0，零梯度占多轮样本 5.7%，纯耗 GPU
完整回复大量丢失多轮对话后半段被整段丢弃保留率仅 45.6%；多轮监督信号只剩名义值的约 37%

问题三：数据本身的重复与失衡。助手回复内容完全相同的占 8.6%（同一答案反复出现会强化背诵式复读）；多轮样本只占 19.4%（单轮:多轮 = 4:1，学「接着聊」的原料本身就少）。

问题四：验证集切偏，训练分数不可信。数据文件按构造有序（前段 100% 单轮、末段 39.4% 多轮），旧的「从文件末尾切验证集」导致验证集多轮占比是训练集的 2 倍多——SFT 验证损失 1.956 与 mini 时代 0.539 不可比，根因在此。

04目标

目标分两类，验证方式完全不同，必须分开看：

  • 第一类（代码修复目标）：只要改完代码、单元测试通过，就必然成立——由代码逻辑本身保证，不需要训练来验证。例如「不完整回复数 = 0」：新的截断逻辑按完整轮次保留对话，结构上不可能产生半截回复。

06阶段 0：免费的能力摸底 + 推理侧应急修复（~1 天，可与阶段 1 并行）

6.1 修正 YaRN 配置错误并测出「纯外推天花板」

已核实的配置错误：YaRN 插值参数 original_max_position_embeddings（含义：告诉插值算法「模型在多长的窗口上训练过」）硬编码为 2048，而模型实际训练窗口只有 380——算法把模型当成「在 2048 内训过」来外推，参数失真，外推质量被系统性低估。

两处硬编码位置：src/minimind_reborn/models/config.py:65（构造处）与 src/minimind_reborn/models/layers.py:45（兜底默认值）。建议抽成常量消除双源。factor 语义 = 目标窗 / 训练窗：套件 B 最高测 2048 → factor 取 6（380×6=2280）。

验收：产出 out/multiturn_eval_yarn.md——不做任何训练时各长度档的切题率/生成长度表。此表回答「训练值不值」：若纯外推已让 1536/2048 档切题，训练侧长上下文的边际收益集中在质量而非能力，档二优先级可下调。

6.2 推理侧应急修复（不改模型，先止住症状）

  • 会话类加 token 预算 + 滑动窗口：历史超预算时丢弃最旧轮次（系统提示恒保留——与阶段 1 训练侧截断策略同构，两侧口径一致）。
  • 推理引擎加输入长度硬校验：超过 32768 时报中文明确错误（「请缩短输入或开启 YaRN」），消灭张量形状裸崩溃。

验收：单测覆盖超限输入与滑窗路径；12 轮长会话末 3 轮重复率在滑窗加持下复测对照。
